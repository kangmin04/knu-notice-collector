# JS Map / 해시테이블 내부 구현 원리

## 2026-09-05 — "Map의 get()이 왜 O(1)인지, 내부적으로 순회를 하는지" 질문에 답하며 정리 (concept-explain 스킬, 인터랙티브 시뮬레이터 아티팩트 동반: https://claude.ai/code/artifact/82b3da81-e14f-46b8-9610-5dec11fce211)

### 핵심 통찰: 탐색을 계산으로 치환
배열 선형탐색은 O(n), 정렬+이진탐색은 조회는 O(log n)이지만 삽입 시 뒤 원소를 밀어야 해서 O(n)으로 여전히 느림. 해시 함수로 "이 키가 몇 번째 칸에 있어야 하는가"를 즉석에서 **계산**해버리면 비교 없이 그 칸으로 바로 점프 가능 — 이게 O(1)("데이터 크기와 무관한 상수 시간")의 실체.

프로젝트 코드 아님 — 개념 설명용 최소 재현:
```js
function hashOf(key, capacity) {
  let sum = 0;
  for (const ch of String(key)) sum += ch.charCodeAt(0);
  return sum % capacity; // 버킷 인덱스
}
```

### get()은 완전히 순회를 안 하는 게 아니라 "짧게만" 순회함
서로 다른 키가 같은 버킷 인덱스로 계산되는 **충돌**은 비둘기집 원리상 필연적. 충돌한 키들은 같은 버킷 안에서 연결 리스트(체이닝)로 엮이고, `get(key)`은 버킷까지는 계산으로 O(1) 점프한 뒤 그 버킷 안의 (평균적으로 원소 1개뿐인) 짧은 체인만 순회하며 실제 `key === key` 비교를 함. "전체 배열 순회"가 아니라 "같은 버킷에 몰린 극소수만 순회"라는 게 O(1)로 취급하는 이유.

### V8의 OrderedHashTable — 왜 버킷 배열과 별도로 데이터 테이블을 두는가
일반 해시테이블은 삽입 순서를 보장하지 않지만, Map 스펙은 "삽입한 순서대로 순회 가능"을 요구함. V8은 이를 위해 **버킷 배열**(해시값 → 데이터 테이블 인덱스)과 **데이터 테이블**(키, 값, 삽입 순서상 다음 엔트리로의 링크)을 분리해서 유지함 — 조회는 해시로 O(1)에 가깝게 하면서 순회는 삽입 순서를 지킴. 이 발상은 Python 3.6+ dict가 도입한 "compact dict" 구조와 동일함.

### 로드 팩터와 리해싱 — amortized O(1)의 조건
로드 팩터(엔트리 수 ÷ 버킷 개수)가 임계치(보통 0.75 근처)를 넘으면 버킷 배열을 키우고 전체 엔트리를 새 버킷 배치로 재계산해서 옮기는 **리해싱**이 일어남. 이 순간은 O(n)이 걸리지만, 전체 삽입 횟수에 걸쳐 나눠 계산(amortized)하면 삽입 1회당 평균은 여전히 O(1)로 수렴함. 즉 "O(1)"은 로드 팩터가 잘 유지된다는 전제 하의 평균 성능이지 항상 보장되는 상한이 아님.

프로젝트 코드 아님 — 개념 설명용 최소 재현:
```js
function maybeRehash(entries, capacity) {
  if (entries.length / capacity > 0.75) {
    return capacity * 2; // 실제로는 여기서 전체 엔트리를 새 capacity로 재배치
  }
  return capacity;
}
```

### 트레이드오프
- 평균 O(1) vs 최악 O(n): 의도적으로 특정 키들만 골라 같은 버킷에 몰리게 만드는 **해시 충돌 공격(hash flooding)**이 가능함. 2011년 전후 PHP/Java/Python 등 다수 웹 프레임워크에서 POST 파라미터 해시 충돌을 악용한 DoS 취약점이 실제 보고됐고, 이후 주요 런타임이 해시 시드를 무작위화하는 계기가 됨.
- Map이 보장하는 순서는 오직 **삽입 순서**뿐 — 키 값 기준 정렬이나 범위 검색("10 이상 20 이하 키 전부")은 불가능. 그런 질의가 필요하면 트리 기반 구조(B-트리 등)가 필요.
- 일반 객체 `{ }`도 V8 내부에서 문자열 키에 대해 dictionary mode(해시 기반)로 전환될 수 있지만, 원래 hidden class 기반 구조라 키를 막 추가/삭제하면 최적화가 깨지기 쉬움. Map은 처음부터 어떤 키 타입(객체, NaN, 함수 등)이든 해시 기반으로 다루도록 설계됨.

### 실무에서 같은 발상이 재등장하는 곳
Java `HashMap`(체이닝 + 버킷당 충돌 8개 초과 시 레드-블랙 트리로 전환하는 treeify 최적화), Redis 해시 타입, 데이터베이스 **해시 인덱스**(`WHERE key = ?` 같은 등가 비교엔 최적이지만 범위 검색엔 못 써서 B-트리 인덱스를 따로 둠), 컴파일러의 심볼 테이블(변수명 → 메모리 주소/타입 매핑)도 대부분 해시테이블로 구현됨.
