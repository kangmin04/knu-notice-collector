# 임베딩 기반 IT 관련성 필터 도입

## Context

수집기(`src/collect.js`)가 경북대 공식 게시판 등에서 새 글을 가져와 노션 "새 글 피드" DB에 자동으로 쌓는데, 같은 사이트(`site.category`가 사이트 고정값)에서도 IT/개발/공모전과 무관한 글(학사일정, 장학금 공지 등)이 섞여 들어오는 문제가 있다. `src/collect.js:83`에 "무관한 데이터 필터링 하고자 item.title로 판단할것"이라는 주석이 이미 남아 있어 item(글) 단위 필터가 필요하다는 인식은 있었지만 방법이 정해지지 않은 상태였다.

`/deep-dive`로 키워드 규칙 / 지도학습(logistic regression) / 비지도학습을 소크라테스식으로 비교한 결과:
- 라벨 데이터가 100건 이하(그중 positive 20~30건)로 너무 적어서, feature를 여러 개 쓰는 logistic regression은 EPV(Events Per Variable) 경험칙(안정적 계수 추정에 positive 샘플 수 대비 feature 10배 필요, Peduzzi et al. 1996)상 과적합 위험이 큼. 20~30건이면 안정적으로 쓸 수 있는 feature는 2~3개뿐.
- 순수 키워드 규칙은 안전하지만, Andrew Ng ML Specialization을 학습 중이라 실제 프로젝트에 임베딩/유사도 개념을 적용해보고 싶어함.
- K-means 같은 비지도학습은 "그룹만 나눠줄 뿐 의미(라벨)는 사람이 붙여야 함"이라는 한계가 있고, TF-IDF류 벡터화는 같은 주제라도 단어가 다르면(예: "해커톤 참가자 모집" vs "아이디어 공모전 안내") 벡터가 멀어지는 문제가 있음.
- 절충안으로 **사전학습된 문장 임베딩 + 프로토타입 문장과의 코사인 유사도(마진) 기반 분류**를 채택. 이 방식은 라벨 데이터를 "학습"이 아니라 "threshold 검증"에만 쓰므로 지도학습만큼의 데이터가 없어도 과적합 위험이 낮고(파라미터를 거의 데이터로부터 추정하지 않음), transfer learning 관점에서 소량 데이터 문제에 대한 표준적인 대응이기도 함.

## 결정된 설계

### 1. Zero-shot에 가까운 프로토타입 유사도 분류
- "IT/개발 관련" 프로토타입 문장들과 "무관(학사/행정/장학금 등)" 프로토타입 문장들을 각각 임베딩해두고, 새 글 제목 임베딩과의 `margin = maxPosSim - maxNegSim`으로 관련 여부를 판단.
- 로컬 추론은 `@xenova/transformers`(transformers.js)의 다국어 sentence-embedding 모델 사용(정확한 모델명/용량은 구현 시 최신 정보로 재확인 — 후보: `Xenova/paraphrase-multilingual-MiniLM-L12-v2`). 외부 API 비용/의존성 없이 처리.

### 2. 파일 구조
```
src/relevance/
  similarity.js       # 순수 함수 cosineSimilarity(a, b) — I/O 없음, 유닛테스트 대상
  similarity.test.js
  prototypes.js       # POSITIVE_PROTOTYPES / NEGATIVE_PROTOTYPES 문장 배열(상수)
  embed.js            # transformers.js pipeline 래핑, 모듈 레벨 singleton으로 lazy-load
  index.js            # scoreTitle(title) → margin, isRelevant(title) → { relevant, score } (threshold 비교 + fail-open)
scripts/
  export-labels-from-notion.js   # 1회성: 노션 "새 글 피드" DB에서 기존 항목을 data/labels.json 스켈레톤으로 export
  tune-threshold.js              # 1회성: data/labels.json으로 threshold별 precision/recall/F1 계산·출력
data/
  labels.json          # { id, title, url, label: true|false|null }[] — seen.json처럼 git으로 추적
```
기존 파서 계약(`{ id, title, url }`)은 변경하지 않는다 — 필터는 title만 입력으로 받는다.

### 3. collect.js 통합 (`src/collect.js:79-92` 부근)
DRY_RUN 여부와 무관하게 필터를 먼저 적용해 DRY_RUN 미리보기가 실제 동작과 일치하게 한다. `isRelevant`가 예외를 던지면(모델 로딩 실패 등) **fail-open**으로 관련 글로 간주하고 경고만 로그 — 필터 오류로 하루치 공지가 통째로 유실되는 걸 방지.

```js
for (const item of newItems) {
  const { relevant, score } = await isRelevant(item.title);
  if (!relevant) {
    console.log(`[SKIP][${site.name}] 무관 판정(score ${score.toFixed(3)}): ${item.title}`);
    seenIds.add(item.id);
    continue;
  }
  if (DRY_RUN) {
    console.log(`[DRY_RUN][${site.name}] 새 글 추가 예정: ${item.title}`);
  } else {
    await addFeedItem({ site, item, notionToken: NOTION_TOKEN, databaseId: FEED_DATABASE_ID });
  }
  seenIds.add(item.id);
}
```
기존 로직(필터 여부와 무관하게 `seenIds.add`가 실행되어 재검토 방지)은 그대로 유지한다.

### 4. 환경변수 (`.env.example` 추가, `src/env.js` 수정 불필요)
```
# 임베딩 기반 IT 관련성 필터 (선택)
# RELEVANCE_THRESHOLD=0        # margin(양성-음성 유사도) 임계값, tune-threshold.js 결과로 채움
# RELEVANCE_FILTER_DISABLED=1  # 문제 생기면 필터 끄고 예전 동작으로 즉시 롤백
```

### 5. 라벨 데이터 확보 → threshold 튜닝 순서
1. `scripts/export-labels-from-notion.js` 실행 — 기존 `NOTION_TOKEN`/`NOTION_FEED_DATABASE_ID`로 "새 글 피드" DB를 조회해 지난 5일치 항목을 `data/labels.json`에 `{id, title, url, label: null}`로 채움 (seen.json에는 id만 있고 title이 없어, 실제 title 텍스트는 노션에서 가져와야 함).
2. `label`을 `true`(IT/개발/공모전 관련)/`false`(무관)로 직접 채움(100건 이하라 수작업 가능한 규모).
3. `scripts/tune-threshold.js` 실행 — `scoreTitle`로 각 항목 margin 계산 후 threshold를 스윕하며 precision/recall/F1 테이블 출력. "무관한 글이 섞이는 게 싫다"는 원래 동기를 고려해 **precision 우선**(F0.5 등)으로 추천 threshold 제시.
4. 선택한 threshold를 `.env`의 `RELEVANCE_THRESHOLD`에 반영.

### 6. CI 캐싱 (`.github/workflows/collect.yml`)
러너가 매일 fresh하게 뜨므로(`data/seen.json`만 실행 후 커밋해 상태를 이어감) 모델 가중치를 매번 새로 받으면 실행 시간·네트워크 의존성이 늘어난다. `env.cacheDir`을 프로젝트 내 고정 경로(예: `.cache/transformers`)로 명시적으로 설정하고 `actions/cache`로 모델명/버전 기준 키로 캐싱하는 스텝을 추가한다. **transformers.js의 정확한 기본 캐시 경로/설정 옵션명은 구현 시점에 설치된 버전 문서로 재확인 필요.**

### 7. 테스트
프로젝트에 테스트 프레임워크가 전혀 없으므로 새 의존성 추가 없이 Node 22 내장 `node:test` + `node:assert` 사용. `package.json`에 `"test": "node --test"` 스크립트 추가. `similarity.test.js`에서 `cosineSimilarity` 순수 함수만 검증(동일 벡터→1, 직교→0, 반대→-1) — 무거운 모델 로딩은 테스트 대상에서 제외해 CI를 빠르고 결정적으로 유지.

## 건드리지 않는 것
- 파서 계약(`{ id, title, url }`) — 필터는 title만 사용하므로 파서 수정 불필요.
- `src/env.js` — 범용 `.env` 파서라 신규 키 추가만으로 충분.
- 필터링된 글도 `seenIds`에는 추가한다 — 다음 실행에서 같은 글이 다시 "새 글"로 재검토되지 않게 하는 기존 로직을 유지.

## 검증 방법
1. `npm install` (`@xenova/transformers` 추가 반영)
2. `node --test` — `cosineSimilarity` 유닛테스트 통과 확인
3. `node scripts/export-labels-from-notion.js` → `data/labels.json`에 기존 항목이 채워지는지 확인 → 수작업 라벨링
4. `node scripts/tune-threshold.js` → precision/recall/F1 테이블 확인, threshold 결정 → `.env` 반영
5. `DRY_RUN=1 npm run collect` 로컬 실행 — `[SKIP]` 로그와 `[DRY_RUN]` 로그를 눈으로 훑어 무관 글이 실제로 걸러지는지, 관련 글이 잘못 걸러지지 않는지 샘플 점검
6. `.github/workflows/collect.yml` 캐싱 스텝 추가 후 실제 Actions 실행 로그에서 모델이 재다운로드 없이(캐시 히트) 정상 동작하는지 확인
7. `npm run lint` — 기존 ESLint 규칙 통과 확인
