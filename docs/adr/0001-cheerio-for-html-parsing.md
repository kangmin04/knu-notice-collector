# 0001 — HTML 파싱에 cheerio 사용

## 상태
승인됨

## 맥락
기존 파서 3종(`gnuboard`/`knuHome`/`knuWbbs`)은 정규식만으로 `<a href=...>` 패턴을 매칭해 목록을 추출한다. 이는 경북대 게시판 9곳처럼 구조가 단순하고 안정적일 때는 동작하지만, 신규로 추가할 13개 정적 파싱 대상 사이트는 각각 CMS/프레임워크가 다르고(전자정부 표준프레임워크, XE, PHP 커스텀, Next.js SSR 등) HTML 구조가 훨씬 복잡하다. 정규식으로 이런 구조를 다루면 중첩 태그, 속성 순서 변화, 줄바꿈 등에 취약해 파서가 쉽게 깨진다.

## 결정
`cheerio`(순수 JS, 네이티브 바이너리 없음)를 도입해 DOM 셀렉터 기반으로 파서를 작성한다. 기존 3개 파서도 cheerio 기반으로 재작성해 파서 계층을 하나의 방식으로 통일한다.

## 결과
- 장점: `$(selector).each(...)`로 구조를 명확하게 표현할 수 있어 유지보수가 쉬워진다. 신규 파서 12개를 각각 독립적으로 작성하기 용이해진다.
- 트레이드오프: cheerio는 htmlparser2 기반이라 속성값의 HTML 엔티티를 자동 디코딩한다. 기존 `knuHome` 파서처럼 원본 href 문자열을 md5 해시해 id로 쓰던 로직은 정규식 시절과 다른 해시값을 낼 수 있다. 실측 결과 `knu-global`(경북대 국제교류처)에서는 이 차이가 실제로 나타났는데, 정확히는 해시가 달라진 게 아니라 **정규식이 홑따옴표 href만 매칭하도록 짜여 있어 쌍따옴표로 작성된 상단 고정("공지") 게시글 12건을 처음부터 계속 놓치고 있었고**, cheerio는 따옴표 스타일을 가리지 않아 이 누락분을 그대로 드러냈다. 버그 수정에 가까운 변화라 별도 마이그레이션 없이 그대로 반영했다.
- **중요한 한계**: cheerio(htmlparser2)가 항상 안전한 것은 아니다. 실측 중 두 가지 실패 사례를 발견했다:
  1. `startup.daegu.go.kr`(DASH) 홈페이지는 마크업이 깨져 있어 cheerio가 실제 `<a>` 태그 303개 중 112개만 파싱했다(나머지가 통째로 누락). 이 사이트는 cheerio 대신 정규식으로 직접 추출한다(`src/parsers/egov.js`의 `parseDash`, 현재는 진짜 게시판을 못 찾아 미사용).
  2. `linkareer.com`/`okky.kr`(Next.js SSR)는 "placeholder svg `<img alt=''/>` 바로 뒤에 실제 썸네일 `<img alt='제목'/>`이 이어지는" 중첩 구조에서 cheerio의 `.text()`가 다음 형제 `<img>` 태그를 통째로 텍스트로 반환하는 것을 확인했다. 이 두 사이트는 `src/parsers/nextSsr.js`에서 정규식으로 카드 블록을 직접 추출한다.

  즉 "정적 파싱 가능"과 "cheerio로 파싱 가능"은 동의어가 아니다 — 새 사이트를 추가할 때 cheerio 결과의 개수/내용이 이상하면(예: 원본 `<a>` 개수와 크게 차이 나면) 정규식 폴백을 의심해봐야 한다.
- 의존성이 0개였던 프로젝트에 첫 외부 의존성이 생기지만, cheerio는 순수 JS라 CI 설치 리스크가 낮다.
